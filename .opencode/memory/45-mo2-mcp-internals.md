34. **Use `IPluginList.onRefreshed`, NOT `IOrganizer.onNextRefresh`, when a broker operation must observe fresh plugin-list state after `organizer.refresh(False)`.** For issue #24, `mo2_install` needed to append fresh plugins to `plugins.txt`, trigger MO2's async refresh, and only then allow a follow-up `mo2_send_plugin_to` to reorder the new plugin. The librarian-confirmed substrate is: `PluginList::refresh` emits `m_Refreshed()` at the tail of `pluginlist.cpp`, after `pluginNames()` / `priority()` / `state()` are current; the Python binding exposes this as `IPluginList.onRefreshed(callback)`. By contrast, `IOrganizer.onNextRefresh` runs from `OrganizerCore::onDirectoryRefreshed` at `m_OnNextRefreshCallbacks()` before `refreshLists()` -> `refreshESPList()` -> `PluginList::refresh`, so `pluginList()` readback there is stale and recreates the race. `onRefreshed` registrations are persistent boost::signals2 callbacks with no Python-visible disconnect; use a per-request one-shot guard (`fired = {"done": False}`) inside the callback and ignore later invocations. Because `organizer.refresh(False)` is a no-op when a refresh is already in flight, the first `onRefreshed` may belong to the pre-existing refresh and may not observe the freshly-written `plugins.txt`; if the settlement check fails, retry exactly once by re-registering the one-shot callback and kicking a second `organizer.refresh(False)`, then return `refresh_attempts` and `refresh_settled`. TS callers must surface `refresh_settled: false` as `registration_mode: "broker_unsettled"` rather than silently reporting normal broker success.
