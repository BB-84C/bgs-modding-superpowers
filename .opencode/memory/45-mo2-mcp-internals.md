## Asset Engine First-Principles Framing (2026-06-27)
- The asset engine (`tools/mo2-assets-engine/`, `tools/mo2-mcp-sidecar/src/mo2_mcp_sidecar/assets.py`) models what the BGS game runtime sees, NOT what MO2's mod-folder organization looks like.
- Game runtime view = ONE virtualized Data tree, projected by USVFS from all enabled mods in priority order. Plugins and BA2s do NOT have to live in the same mod folder; the runtime sees a unified Data/.
- "Mod" in the engine model is an ATTRIBUTION LABEL on each provider in the unified tree, NOT an enumeration unit. The substrate is the tree; mods answer "who provided this path?" as metadata.
- Mechanical self-check for any new function or data structure: if it takes a single mod and computes a CONFLICT property of that mod's contents in isolation, that is per-mod-scope thinking and is wrong. If it takes a mod and computes which paths the mod PROJECTS into the unified tree (the VFS projection step), then aggregation across mods builds the substrate, that is correct.
- Symptom of backslide: field names like `archives_unenumerated` on per-mod result shapes; functions that walk a mod's folder and assume the mod's plugin and the mod's BA2s are co-located; conflict resolution per-mod-folder instead of per-virtual-path.
- Substrate location: `tools/mo2-assets-engine/src/mo2_assets_engine/virtual_data_tree.py` is the center. `mod_enumerator` is the VFS-projection helper called from inside the tree builder. `conflict_resolver.resolve_tree()` operates on `tree.file_providers`, a `dict[relative_path, list[Provider]]` keyed by virtual path.
- Winner rule (BGS runtime fidelity): LOOSE always beats ARCHIVED at the same path; among LOOSE: highest mod_priority wins; among ARCHIVED: highest plugin_load_order wins (BA2 load order derives from plugin load order). One unified resolver, no bucketing of conflicts by source type — `winner.source_type` and `losers[*].source_type` are presentation labels, not substrate categories.
- Reference: 2026-06-27 substrate rebuild commits `a0d7ed8` (substrate add), `64f8656` `924e371` `902e32d` `03e5fc6` (consumer refactor), `b2f679c` (BA2-as-file scope rollback because the BA2 reader does not yet cover Starfield v3/LZ4).

## BA2/BSA Archive Treatment (2026-06-27)
- The engine's BA2 reader currently supports `_SUPPORTED_VERSIONS = {1, 2, 8}` only. Starfield real-world modsets include v3 (DX10/LZ4) archives — empirically 17 of 202 enabled archives in the BB84自用2 audit profile. Opening v3 crashes the reader.
- Current scope decision (2026-06-27 BB84 explicit direction): the engine does NOT open `.ba2`/`.bsa` at all. `.ba2`/`.bsa` at mod-root are treated as projected loose paths (USVFS projects them into Data/<archive_name>.{ba2,bsa} as files). Two mods shipping the same archive name produce a clean file-to-file conflict on the archive path; higher mod_priority wins, the other is hidden.
- Plugin/Archive metadata + cross-folder attachment metadata (`tree.attachments`) IS still populated for informational use. The agent can see which archives belong to which plugin without the engine opening them. No archive-source `Provider` entries are produced in `file_providers`.
- Future scope expansion: when the engine BA2 reader covers v3/v4/v5/v7 (and LZ4 decompression for member-name table is verified — names are NOT compressed, only data is, so listing members might work without LZ4 dep), member-level enumeration can return by re-populating the archive-loop in `build_virtual_data_tree`. The substrate model already supports it; only the `enumerate_archive_member_paths` call site needs to be re-enabled. Keep the regression guard test `test_archives_are_projected_as_loose_files_and_never_opened` in mind — it uses invalid BA2 bytes as bait to ensure no accidental archive opening.
- Sister tool `tools/bgs-archive` is the standalone CLI for archive inspection/extraction; it has independent reader code. If the engine ever needs to share BA2 parsing, refactor into a common library rather than duplicating — but that's a separate architectural decision, not a today fix.
Treat BGS asset/conflict computation as the unified virtual `Data/` tree the runtime sees, not as mod-folder-local conflict math. A plugin in one enabled mod can make archives from other enabled mods load when archive naming matches globally, so archive attachment must search the global enabled plugin/archive pool across folders. For `conflict_preview` and the BGS resource auditor, compute per-path provider sets across loose files and attached archives together, then resolve winners from runtime rules (`loose > archive`; loose-vs-loose by mod priority; archive-vs-archive by attached plugin load order). Bucket labels are presentation only; do not let `archives_unenumerated` or folder-local scope hide whether an archive is effectively loaded.
